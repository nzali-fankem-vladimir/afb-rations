## 1. CONTEXTE DU PROJET

Digitalisation du paiement des frais de ration et de transport des agents de la garde armée d'Afriland First Bank. Aujourd'hui le processus est manuel : saisie papier jour par jour, consolidation mensuelle à la main, validations par visas physiques, remontée hiérarchique selon le montant.

Le module dématérialise ce cycle, de la saisie journalière jusqu'à la mise à disposition de l'état validé pour la comptabilité. Il fait partie d'un programme plus large piloté par la Direction Financière et Trésorerie (dotations téléphoniques, solde de tout compte, prime de stage, primes de permanence, rations et transport garde armée).

Le module s'intègre au portail interne INTRA en application liée autonome, avec un realm Keycloak partagé.

## 2. STACK TECHNIQUE (décisions figées, ne pas dévier)

- **Architecture intérieure : microservices**, chaque service déployable et conteneurisé indépendamment. Pas de monolithe.
- **Backend :** Spring Boot 4.1.0, Java 21 (Temurin), Maven.
- **Frontend :** React 19 + TypeScript, Vite, Tailwind CSS, axios. Pas de JavaScript nu.
- **Base de données :** PostgreSQL 16, une base par service.
- **ORM :** Spring Data JPA / Hibernate.
- **Migrations :** Flyway, un jeu de migrations versionné par service.
- **Sécurité :** Spring Security + OAuth2 Resource Server, adossé à Keycloak. Flux Authorization Code + PKCE. Sessions stateless.
- **Passerelle :** Spring Cloud Gateway. **Registre :** Eureka. Spring Cloud 2025.1.2.
- **Messagerie :** Apache Kafka, pour l'échange avec la comptabilité et pour le journal d'audit.
- **PDF :** iText 8 (artefacts `kernel` et `layout`). **Excel :** Apache POI.
- **Doc API :** Springdoc OpenAPI (swagger-ui par service, accès interne).
- **Conteneurisation :** Docker, registre privé Harbor, orchestration Kubernetes.

Ne jamais réintroduire : EHR, enrôlement, fonctions éligibles, mot de passe applicatif, troisième niveau de validation RH. Ces éléments viennent d'autres modules et ne concernent pas ce projet.

Communication synchrone en REST via la passerelle. Communication asynchrone via Kafka pour l'échange comptable et pour l'audit.

**Pourquoi un service Audit dédié.** Le cahier des charges exige un journal immuable. Un journal réparti en une table par service laisserait chaque service maître de ses propres traces, avec les pleins droits dessus. Un service dédié rend la base d'audit inaccessible en modification depuis les services métier : l'immuabilité devient une propriété de l'architecture, pas une discipline de code. C'est un argument de contrôle interne autant que d'architecture.

**Une bibliothèque partagée, pas un huitième service.** Le module Maven `rations-audit-commun` (Sprint 1.3) porte la publication d'audit reprise par les six services métier. Ce n'est pas un service : il n'a ni base, ni port, ni conteneur, et ne se déploie pas. C'est la seule mutualisation de code du backend, son périmètre est vérifié au build, et l'ajouter à un service ne crée aucune dépendance d'exécution vers un autre service. Voir `docs/publication-audit.md`.

Structure interne de chaque service (dépendances vers l'intérieur, le domaine ne dépend d'aucune couche technique) :

```
service-xxx/
  api/            controllers REST + DTO
  application/    services applicatifs, orchestration
  domaine/        entités, règles de gestion
  infrastructure/ repositories JPA, clients REST, producteurs/consommateurs Kafka
                  config/ SecurityConfig par service
```

## 4. MODÈLE DE DONNÉES : 10 TABLES

Conventions : PostgreSQL 16, `snake_case`, PK `id BIGINT` auto-incrémentée, dates en `TIMESTAMP`, montants en entier (FCFA).

Répartition par base :

| Base | Tables |
| --- | --- |
| `rations_identite` | `utilisateurs` |
| `rations_saisie` | `beneficiaires`, `fiche_journaliere`, `ligne_prestation` |
| `rations_grilles` | `grille_tarifaire` |
| `rations_workflow` | `processus_mensuel`, `etape_workflow`, `piece_jointe`, `parametre_systeme` |
| `rations_audit` | `audit_log` |

- **utilisateurs** — projection locale du compte annuaire. `login` (prenom_nom), `sub_keycloak`, `role`, `code_unite`. Complétée en pratique de `matricule`, `email`, `actif`, `date_dernier_acces` (décision Sprint 0.7, section 17). AUCUN mot de passe.
- **beneficiaires** — agent servi. `nom`, `prenom`, `num_compte_courant`, `code_agence`. Créé au fil des saisies, pas d'enrôlement.
- **grille_tarifaire** — `nature`, `session`, `montant_fcfa`, `statut_validation`, `id_createur` (ARH), `id_validateur` (DRH). Une seule grille ACTIVE avec `date_fin NULL` par couple (nature, session).
- **processus_mensuel** — `mois_paiement`, `annee_paiement`, `code_unite`, `type_processus`, `id_processus_origine`, `motif_ouverture`, `montant_total`, `statut`, `transmis_comptabilite`. Un seul processus NORMAL par (code_unite, mois, année) ; plusieurs COMPLEMENTAIRE possibles. Complétée de `statut_integration`, `reference_comptable`, `date_traitement`, `motif_integration` (migration V4, Sprint 5.1) : le contrat d'API §7.2 expose un statut d'intégration à trois valeurs que le booléen ne peut pas porter, et le service Transmission n'a pas de base. **Les quatre colonnes sont nullables** — un état jamais transmis n'a aucun statut d'intégration, pas `EN_ATTENTE`. Une contrainte `ck_processus_integration_apres_transmission` interdit un statut d'intégration sans transmission. Complétée enfin de `date_reservation_transmission` (migration V5, Sprint 5.3) : le verrou de RG-13 réserve la transmission **avant** de publier, et sans horodatage un état publié il y a 200 ms serait indiscernable en base d'un état publié il y a trois jours dont on ignore l'issue. Les quatre situations se lisent alors sur le couple (`transmis_comptabilite`, `statut_integration`), et leur ancienneté sur cette colonne : `(false, nul)` jamais transmis, **`(true, nul)` réservé sans publication confirmée**, `(true, EN_ATTENTE)` publié sans accusé, `(true, INTEGRE|REJETE)` la comptabilité a répondu.
- **fiche_journaliere** — `id_processus`, `date_jour`, `statut`. Unicité (id_processus, date_jour).
- **ligne_prestation** — `id_fiche_journaliere`, `id_beneficiaire`, `nature`, `session`, `montant_applique`. Montant figé à la saisie.
- **etape_workflow** — `id_processus`, `id_acteur`, `ordre_etape`, `nom_etape`, `statut_etape`, `motif_retour`, `signature_numerique`.
- **piece_jointe** — UN SEUL document par processus (`id_processus` unique), enrichi progressivement des signatures. Complétée de `nombre_signatures` (migration V3, Sprint 4.2) : il compte les signatures **réellement écrites dans le fichier PDF**, et n'est incrémenté qu'**après confirmation d'écriture disque** (fsync + renommage atomique), jamais dans la même transaction que `etape_workflow` — sinon il ne mesurerait que le circuit, que `etape_workflow` décrit déjà.
- **parametre_systeme** — `code`, `libelle`, `valeur`, `actif`. Porte le seuil d'aiguillage et les drapeaux de fonctionnalité.
- **audit_log** — journal immuable, **base `rations_audit`, service Audit**. `id_utilisateur`, `service_emetteur`, `action`, `entite_cible`, `id_entite`, `date_action`, `adresse_ip`, `detail_json`. Aucune méthode de modification ni de suppression n'est exposée, y compris celles héritées par défaut du repository.

**Convention transverse.** Une colonne `date_creation` (`TIMESTAMP`, défaut `CURRENT_TIMESTAMP`) est ajoutée à chaque table métier pour l'audit technique, sauf `parametre_systeme` (sans horodatage propre) et `audit_log` (porte `date_action`). Décision Sprint 0.7, section 17.

**CODE AGENCE ≠ CODE UNITE.** Même format (VARCHAR(5), référentiel des codes guichets Afriland), mais rôles distincts. `code_agence` = agence de domiciliation du compte du bénéficiaire (ligne de crédit). `code_unite` = unité qui supporte la charge (ligne de débit). Toujours les distinguer.

## 6. RÈGLES MÉTIER CRITIQUES (appliquer sans exception)

- **RG-01** Nature : chaque ligne est RATION ou TRANSPORT exclusivement.
- **RG-02** Session : chaque ligne est JOUR ou SOIR exclusivement.
- **RG-03** Montant automatique : repris de la grille ACTIVE (nature, session). Jamais saisi à la main.
- **RG-04** Unicité journalière : pas deux fois le même bénéficiaire pour la même journée (même nature, même session).
- **RG-05** Fiche vierge par jour : chaque nouveau jour ouvre une fiche réinitialisée.
- **RG-06** Consolidation mensuelle automatique par unité.
- **RG-07** Validation séquentielle : agent → DA → DR le cas échéant. Aucun saut de niveau.
- **RG-08** Seuil d'aiguillage : après validation DA, état ≤ 100 000 XAF clôturé et transmis ; > 100 000 XAF envoyé au DR. Seuil lu dans `parametre_systeme`, jamais codé en dur. **La comparaison n'existe qu'à un seul endroit du module** : `AiguillageService.aiguiller` (service Workflow). Ni la machine à états, ni le service de validation, ni le contrôleur n'en refont une. Voir `docs/decisions/2026-09-01-seuil-aiguillage-et-borne.md`. **Seuil absent, désactivé ou illisible : refus, jamais une valeur de repli** — `500 SEUIL_INDISPONIBLE`, journalisé au préfixe repérable `SEUIL INDISPONIBLE`. Un seuil négatif est refusé, un seuil de zéro est accepté. **Jamais mis en cache** : relu à chaque validation, CT-18 faisant précisément varier le paramètre à chaud. Le seuil n'est lu **qu'au premier niveau** : après le visa du directeur réseau il n'y a plus d'échelon, donc rien à arbitrer.
- **RG-09** Signature numérique horodatée à chaque validation, sur la pièce jointe unique. **Nature : mention horodatée + empreinte SHA-256, pas de cryptographie** (Sprint 4.2). Sur le document : login, rôle figé, date et heure, dans un cadre dédié de la dernière page. En base : `SHA-256:<hexa>` dans `etape_workflow.signature_numerique`. Le login plutôt que le nom d'usage, parce qu'il est la clé de rapprochement avec le journal d'audit et qu'il est stable. **Ce n'est pas une signature au sens juridique** : l'empreinte détecte une altération du fichier, pas une falsification coordonnée, et seule la dernière reste vérifiable, le fichier changeant à chaque enrichissement. Un **retour n'est pas une validation** et n'appose donc aucune signature. Intégration au service de signature de la banque : point ouvert côté DSI.
- **RG-10** Motif obligatoire pour tout rejet ou retour.
- **RG-11** Retour toujours vers l'agent d'unité, quel que soit le niveau d'origine. Rendu **structurel** : les deux transitions de retour d'ET01 mènent au même et unique statut `RETOURNE`, il n'existe aucune cible intermédiaire à choisir.
- **RG-12** Séparation des tâches : un même utilisateur ne cumule pas saisie et validation multi-niveau d'un même dossier, et ne choisit pas son N+1. **Le contrôle porte sur le cycle courant** — les étapes postérieures ou égales à la dernière `SOUMISSION_AGENT` —, jamais sur toute la vie du processus : un retour clôt un cycle, et ce qui y a été fait ne pèse plus contre personne au cycle suivant. Sans cela, l'unique chef d'unité d'une agence serait définitivement incapable de valider un état qu'il a lui-même retourné pour correction. Refus en `403 SEPARATION_TACHES`, code distinct des deux autres refus en 403. Voir `docs/decisions/2026-09-01-separation-des-taches-et-cycle-de-validation.md`.
- **RG-13** Transmission unique : un état validé n'est transmis qu'une fois (`transmis_comptabilite`).
- **RG-14** Validation DRH des grilles : toute grille passe EN_ATTENTE_DRH, la DRH valide (ACTIVE, ancienne fermée) ou rejette avec motif. Une seule active par (nature, session).
- **RG-15** Unicité inter-états : aucune ligne ne peut reproduire une combinaison (bénéficiaire, journée, nature, session) déjà présente dans un autre état de la même unité et de la même période. Contrôle sur `processus_mensuel` + `fiche_journaliere` + `ligne_prestation`.

**Ce qu'est un « état complet » — les quatre contrôles de la soumission** (Sprint 4.2, point K-04
soldé à la clôture du Sprint 4). Le service Workflow refuse la soumission en `422 ETAT_INCOMPLET`,
accompagné du champ `manques` (§11), quand l'un de ces quatre contrôles échoue :

| Contrôle | Refus | Pourquoi |
| --- | --- | --- |
| **État vide** | aucune ligne de prestation | Un état sans ligne n'engage rien et produirait un montant total de zéro que l'aiguillage traiterait comme un dossier légitime. |
| **Ligne hors période** | une ligne datée hors du mois et de l'année de l'état | Une ligne de mars glissée dans l'état de septembre échappe au contrôle d'unicité RG-15 de mars, donc **devient payable deux fois**. |
| **Ligne sans montant** | `montant_applique` nul ou négatif | Contredit RG-03 : le montant vient de la grille active et n'est jamais absent. |
| **Bénéficiaire sans compte courant** | `num_compte_courant` vide | La ligne de crédit serait impossible à produire côté comptabilité. |

**Le contrôle de période porte sur les LIGNES, jamais sur les JOURNÉES** : il n'existe aucun
`DELETE /saisie/fiches/{id}` au contrat, et bloquer sur une journée vide égarée enfermerait
définitivement l'agent, qui ne peut supprimer que des lignes. **Un manque par contrôle**, jamais un
par ligne fautive : au plus quatre entrées, cinq exemples nommés, le reste annoncé en nombre. Les
contrôles écartés et leurs motifs restent détaillés dans `docs/controles-completude.md`.

## 7. WORKFLOW ET AIGUILLAGE

```
Agent : saisie journalière → consolidation → soumission (signature agent)
      → Chef d'Unité (DA) : valide ou retourne (motif)
          si montant ≤ 100 000 XAF : CLOTURE + transmission comptable
          si montant > 100 000 XAF : → Directeur Réseau (DR) : valide ou retourne
              validation DR : CLOTURE + transmission comptable
```

Tout retour (DA ou DR) ramène l'état à l'agent (RETOURNE), jamais à un niveau intermédiaire. L'état CLOTURE est définitif.

**État complémentaire (régularisation).** Un bénéficiaire signale hors système un oubli sur un mois clôturé. L'agent ouvre un `processus_mensuel` de type COMPLEMENTAIRE qui référence l'état d'origine (jamais rouvert). À chaque ligne, RG-15 est vérifiée. Le circuit de validation est identique à un état normal. **Fonctionnalité livrée mais fermée par le drapeau `RATTRAPAGE_ACTIF` dans `parametre_systeme`, tant que le métier n'a pas confirmé.**

## 9. ÉCHANGES KAFKA (trois topics)

Noms de développement (Sprint 0.5) : `rations.etat.valide`, `rations.etat.accuse`, `rations.audit.evenement`. Nommage définitif en environnement partagé non arrêté (point DSI D-07, voir `docs/points-en-attente.md`) : ne pas figer ces noms ailleurs que dans `infra/docker/kafka-topics.sh`.

### 9.1 Échange comptable (producteur ET consommateur)

- **Publie** sur `rations.etat.valide` à la clôture : période, code unité, type, montant total, et le détail des lignes (nom, prénom, compte courant, **code agence**, nature, session, montant).
- **Consomme** sur `rations.etat.accuse` l'accusé du module de comptabilisation : `statut_integration` (EN_ATTENTE | INTEGRE | REJETE), référence comptable, date. Met à jour le statut d'intégration du processus, remonté dans le suivi.

**Le consommateur ne tombe jamais sur un message illisible** (Sprint 5.2). Désérialisation en
**chaîne** (`StringDeserializer`), jamais `JsonDeserializer` : celui-ci échouerait *dans* le
conteneur Kafka, hors de portée du code, et le message empoisonné serait rejoué sans fin en
bloquant tous les accusés suivants, valides compris. La conversion JSON a lieu dans le code,
sous capture.

**Le traitement est idempotent, et l'idempotence vit côté Workflow.** Le service Transmission
n'a pas de base : c'est le service Workflow qui compare l'accusé à ce qu'il détient **et écrit
dans la même transaction**, puis rend `APPLIQUE` ou `DEJA_APPLIQUE`. Lire puis décider puis
écrire en deux appels laisserait entre les deux une fenêtre où un second accusé pourrait
s'intercaler. Un rejeu à l'identique n'écrit rien et **ne publie aucune trace d'audit** : une
seconde ligne ferait croire à un second traitement comptable.

**Table des transitions du statut d'intégration** (`TransitionIntegration`, service Workflow,
mutateur d'entité en visibilité paquet) : `NULL` et `EN_ATTENTE` sont **ouverts** — identique
en tout point = déjà appliqué, sinon appliqué ; `INTEGRE` et `REJETE` sont **définitifs** —
identique = déjà appliqué, **tout le reste = contradiction**. **Aucun accusé ne fait régresser
un statut**, ce qui rend un rejeu de topic inoffensif *même dans le désordre*. Un état jamais
transmis refuse tout accusé (`422 PROCESSUS_NON_TRANSMIS`) et **le drapeau de transmission
n'est jamais posé à cette occasion**. Voir `docs/decisions/2026-09-02-consommation-accuse-comptable.md`.

**Cinq anomalies, toutes définitives, toutes tracées puis avancées** : message illisible
(`ACCUSE ILLISIBLE`), processus inconnu (`ACCUSE ORPHELIN`), jamais transmis
(`ACCUSE INCOHERENT`), accusé contradictoire (`ACCUSE CONTRADICTOIRE`), charge invalide
(`ACCUSE INVALIDE`). **Le seul échec temporaire est un service Workflow injoignable** : lui
seul fait lever le consommateur et rejouer, avec un réessai **borné** (2 tentatives, 2 s) puis
abandon tracé (`ACCUSE ABANDONNE`). Acquittement **après** traitement, un seul fil.

Le service Transmission n'expose **aucun endpoint de déclenchement au client** : la transmission est déclenchée par le service Workflow à la clôture, par l'endpoint **interne** `POST /transmission/processus/{id}` (Sprint 5.1, hors contrat passerelle, §11). Ce service **n'a aucune base** : il relit l'en-tête du processus auprès du Workflow et le détail des lignes auprès de la Saisie, par leurs API et jamais par leurs bases (AR04), puis **vérifie lui-même que l'état est `CLOTURE`** avant de publier — un endpoint qui publierait sur la foi d'un corps fourni par l'appelant enverrait en paiement n'importe quel état.

**RG-13 : réserver, publier, confirmer — dans cet ordre** (Sprint 5.3). Le verrou d'unicité vit sur
`processus_mensuel`, dans la base du service Workflow, et se demande par l'endpoint **interne**
`PUT /processus/{id}/transmission` (trois étapes : `RESERVATION`, `CONFIRMATION`, `LIBERATION`). Le service
Transmission le revendique **pendant sa propre requête**, juste avant de publier et après avoir épuisé tous les
refus possibles : un verrou posé en amont par le Workflow serait entièrement contourné par un appel manuel de
`POST /transmission/processus/{id}`, l'un des chemins de double transmission (CT-22).

**Pourquoi avant et non après.** Marquer après une publication réussie laisse republier si le marquage échoue —
double paiement, irréversible. Réserver avant laisse un état réputé transmis sans l'être — un impayé **visible et
réparable**. On retient le second parce que son risque se voit et se répare, et l'autre non.

**La réservation ne pose que le drapeau et l'horodatage** ; `statut_integration` reste **nul** jusqu'à la
confirmation. C'est ce qui distingue « publié, la comptabilité n'a pas répondu » de « réservé, on ignore si
l'événement est parti », et toute la détectabilité du dispositif tient là.

**Résistance à la concurrence : `SELECT ... FOR UPDATE`** (`LockModeType.PESSIMISTIC_WRITE`) sur la ligne du
processus. Deux instances qui réservent le même état sont sérialisées par PostgreSQL : la seconde attend le commit
de la première, puis lit le drapeau déjà posé. Un contrôle en deux temps — lire, publier, écrire — n'en séparerait
aucune. Transactions **courtes et sans appel réseau** (`REQUIRES_NEW`) : tenir la ligne verrouillée pendant la
publication bloquerait toute lecture concurrente du même dossier.

**La libération n'a lieu que sur la preuve qu'aucun événement n'est parti.** `ResultatPublication` distingue
`EchecAvantEnvoi` (sérialisation impossible, `send()` qui lève dès l'appel : rien n'a quitté la machine → verrou
**libéré**, reprise possible) de `EchecIssueIncertaine` (délai d'accusé dépassé, échec de livraison → verrou
**conservé**). Symétrique exact de `ResultatDemandeTransmission` côté Workflow, et même règle : **ne jamais
republier ce qui a pu partir**.

**Une seconde demande n'est pas une erreur** : `200` avec `resultat: DEJA_TRANSMIS`, jamais un code d'erreur qui
ferait croire à une panne et pousserait à réessayer. Idiome `APPLIQUE` / `DEJA_APPLIQUE` du Sprint 5.2.

**Supervision.** Un état `CLOTURE` réservé depuis longtemps sans statut d'intégration est une publication d'issue
incertaine, à lever à la main après vérification du topic — le module ne la rejoue jamais de lui-même. La requête
`statut = 'CLOTURE' AND transmis_comptabilite = TRUE AND statut_integration IS NULL AND date_reservation_transmission < NOW() - INTERVAL '15 minutes'`
la détecte ; elle est à surveiller au même titre que `statut = 'CLOTURE' AND transmis_comptabilite = false`. Voir
`docs/decisions/2026-09-03-unicite-de-transmission-et-verrou.md`.

**Un échec de transmission n'annule jamais la clôture** : le document porte déjà le visa, écrit sur disque hors transaction (Sprint 4.2), et faire dépendre une validation de la banque de la disponibilité de Kafka serait absurde. L'échec est signalé trois fois — journal au préfixe `TRANSMISSION MANQUEE`, événement d'audit `TRANSMISSION_MANQUEE`, et champ `transmission` rendu au valideur —, et le drapeau reste à faux, ce qui laisse l'état retrouvable par requête.

**On ne rejoue jamais une transmission qui a pu partir.** L'idempotence du producteur Kafka ne couvre que les réessais internes d'un même `send()` ; un second `send()` applicatif est un message neuf. Le réessai (une seule fois, pause 2 s) est donc réservé aux échecs **antérieurs à toute publication**, ce que le type `ResultatDemandeTransmission` distingue structurellement. Voir `docs/decisions/2026-09-02-transmission-comptable-et-reprise.md`.

### 9.2 Journal d'audit (six producteurs, un consommateur)

- **Les six services métier publient** sur `rations.audit.evenement` après chaque action significative : identifiant utilisateur, service émetteur, action, entité ciblée, identifiant d'entité, horodatage, adresse IP, delta avant/après.
- **Le service Audit consomme** ce topic et écrit dans `audit_log`.

**Le producteur est mutualisé, pas réécrit par service.** Le module Maven `rations-audit-commun` (décision Sprint 1.3) porte la charge de l'événement, le port `PublicateurAudit` et le producteur Kafka. Les six services métier en dépendent ; **le service Audit n'en dépend pas** (il consomme le topic en *tolerant reader*, avec son propre type, pour que le schéma puisse évoluer sans pas cadencé à sept services). Ne jamais réécrire un producteur d'audit local, ni surcharger les réglages du producteur du module — `max.block.ms` en tête : ce sont eux qui garantissent que l'audit ne fait jamais échouer le métier.

**Tout service consommateur de `GET /identite/habilitation` doit publier un événement `ACCES_REFUSE`** quand le verdict est négatif, et quand le service Identité est injoignable. Le service Identité ne trace pas ces refus : il répond à une question, il ne refuse pas l'action — c'est le consommateur qui refuse. **Si le consommateur ne publie pas, le refus n'est tracé nulle part**, et l'exigence CT-04 n'est pas tenue, en silence. Voir `docs/appel-habilitation.md`.

**L'écriture d'audit est asynchrone par construction.** Un service métier publie et poursuit son traitement : il n'attend aucune réponse et ne dépend pas de la disponibilité du service Audit. C'est ce qui garantit le principe selon lequel l'audit ne fait jamais échouer une opération métier. Un appel REST synchrone vers le service Audit est **interdit** : il réintroduirait exactement la dépendance que ce choix élimine.

**Périmètre définitif des opérations publiant un événement d'audit** (arrêté au Sprint 6.3,
après inventaire des 30 points de publication du backend).

| Service | Actions publiées |
| --- | --- |
| Identité | `ATTRIBUTION_ROLE`, **`LIAISON_COMPTE_KEYCLOAK`**, `ACCES_REFUSE` |
| Grilles | `CREATION_GRILLE`, `SOUMISSION_GRILLE`, `VALIDATION_GRILLE`, `FERMETURE_GRILLE`, `REJET_GRILLE`, `ACCES_REFUSE` |
| Saisie | `OUVERTURE_FICHE_JOURNALIERE`, `CREATION_LIGNE_PRESTATION`, `MODIFICATION_LIGNE_PRESTATION`, `SUPPRESSION_LIGNE_PRESTATION`, **`CREATION_BENEFICIAIRE`**, `INCOHERENCE_BENEFICIAIRE`, `ACCES_REFUSE` |
| Workflow | `DECLENCHEMENT_PROCESSUS`, `SOUMISSION_PROCESSUS`, `VALIDATION_PROCESSUS` (porte la clôture dans son delta), `RETOUR_PROCESSUS`, `INTEGRATION_COMPTABLE`, `TRANSMISSION_COMPTABLE`, `TRANSMISSION_MANQUEE`, `TRANSMISSION_DOUBLON_REFUSEE`, `TRANSMISSION_RESERVATION_LIBEREE`, `ACCES_REFUSE` |
| Transmission | `TRANSMISSION_ETAT_VALIDE`, `TRANSMISSION_REFUSEE`, `TRANSMISSION_CONFIRMATION_MANQUEE`, `ACCUSE_COMPTABLE_APPLIQUE`, `ACCUSE_COMPTABLE_REFUSE`, `ACCES_REFUSE` |
| Reporting | **`GENERATION_RAPPORT`**, **`EXPORT_RAPPORT`** |

**Ce qui n'est délibérément pas tracé, et pourquoi.** Les **lectures de travail** —
`GET /reporting/demandes`, `GET /reporting/processus/{id}/historique`, et toutes les
consultations des autres services — ne publient rien : un événement par affichage d'écran
noierait les faits notables. Idem pour `utilisateurs.date_dernier_acces`, écrit à chaque
requête. La ligne est : **on trace ce qui modifie un état, ce qui agrège une portée entière,
ou ce qui fait sortir un fichier du système — pas ce qui affiche un dossier.** Un export en
est le cas limite : c'est le seul geste du module qui produit un fichier quittant
définitivement le périmètre applicatif, où plus aucune habilitation ne le protège.

**`service_emetteur` et l'ordre « modification puis publication » sont garantis par construction,
pas par discipline.** Le premier est estampillé par le producteur depuis `spring.application.name`
(`EvenementAudit.avecServiceEmetteur`), jamais rempli à la main — aucun service ne peut publier une
trace anonyme. Le second tient à `@TransactionalEventListener(AFTER_COMMIT)` : un rollback ne laisse
jamais derrière lui la trace d'une opération qui n'a pas eu lieu.

**L'ordre d'arrivée sur le topic n'est PAS l'ordre des faits : tout tri du journal se fait sur `date_action`, jamais sur `id` ni sur l'offset.** Constaté sur des messages réels au Sprint 6.3 — le bénéficiaire créé à `16:56:27.698` est arrivé à l'offset 179, la ligne qui le référence, créée à `16:56:28.414`, à l'offset 178. Le pool `@Async("executeurAudit")` émet après le commit sur plusieurs threads, et la clé de partition (`entiteCible:idEntite`) n'ordonne que les événements d'une **même** entité, pas ceux d'entités différentes. L'ordre vrai reste intégralement récupérable parce qu'`EvenementAudit` **horodate au moment de l'action, pas à la publication** — c'est écrit dans sa javadoc et c'est précisément la situation que cette précaution couvre. Les deux endpoints de consultation du service Audit devront donc trier sur `date_action` ; l'index `idx_audit_log_date_action` existe depuis la V1.

**`idUtilisateur` et `idEntite` sont nullables, et la migration V2 de `rations_audit` le reconnaît.**
La V1 les déclarait `NOT NULL`, ce qui aurait rejeté 21 des 30 traces du backend — à commencer par
les six `ACCES_REFUSE` de CT-04, précisément les plus importantes à conserver. **Aucune valeur
sentinelle** (`-1` et consorts) : elle fabriquerait un utilisateur qui n'existe pas et qu'une jointure
prendrait pour réel. Conséquence connue et consignée : une recherche par `id_utilisateur` ne voit pas
les 21 traces qui le laissent nul (`docs/points-en-attente.md`, point **A-01**).

## 10. AUTHENTIFICATION KEYCLOAK

- Connexion = redirection du frontend vers Keycloak (Authorization Code + PKCE). Aucun service n'émet de jeton.
- Les services valident le jeton (OAuth2 Resource Server), en extraient l'identité (`sub_keycloak`) et le rôle.
- `utilisateurs` est une projection locale : `login`, `sub_keycloak`, `role`, `code_unite`. Le rôle applicatif et le code unité sont gérés localement, pas dans l'annuaire.
- **Création du profil local (décision Sprint 0.4) : pré-provisionnement puis liaison automatique.** L'administrateur ouvre le profil (`login`, `role`, `code_unite`) sans connaître le `sub_keycloak`. À la première connexion, le service Identité rapproche le profil par le `login` et y inscrit le `sub` ; les connexions suivantes passent directement par le `sub`. Un jeton valide sans profil local correspondant est refusé (403) : l'habilitation au module reste un acte d'administration explicite, elle ne découle pas de la seule existence d'un compte à l'annuaire.
- **Ne jamais** ajouter de champ mot de passe, ni de route de login côté backend.
- En développement : realm de dev Keycloak sur localhost:8180 ; en production : realm AFB partagé.
- Chaque service porte une `SecurityConfig` dans `infrastructure/config`. La sonde `/actuator/health` est la seule route métier publique.
- **Documentation Springdoc** (`/swagger-ui.html`, `/swagger-ui/**`, `/v3/api-docs`, `/v3/api-docs/**`) : « accès interne » (section 2) signifie exposée sans jeton, mais réservée au réseau interne — distinct des routes métier, qui restent toutes protégées par OAuth2. Chaque `SecurityConfig` doit donc les déclarer `permitAll()` en `GET`, à côté de la sonde de santé, pour rester consultable directement au navigateur.

## 15. ERREURS À NE JAMAIS COMMETTRE

- Coder le seuil de 100 000 XAF en dur (toujours via `parametre_systeme`).
- Confondre ou fusionner `code_agence` et `code_unite`.
- Stocker un mot de passe ou créer une route de login backend.
- Générer des écritures comptables ou simuler un impact CBS dans ce module.
- Réintroduire l'enrôlement, l'EHR ou les fonctions éligibles.
- Laisser un montant saisi manuellement au lieu de la grille active.
- Permettre un retour vers un niveau intermédiaire au lieu de l'agent.
- Transmettre deux fois le même état à la comptabilité.
- Rouvrir un état clôturé pour une régularisation (créer un état COMPLEMENTAIRE à la place).
- Oublier le contrôle d'unicité inter-états (RG-15) à la saisie d'une ligne de régularisation.
- **Appeler le service Audit en REST synchrone depuis un service métier** (l'audit passe par le topic Kafka, jamais par un appel bloquant).
- **Exposer un endpoint d'écriture sur le service Audit** ou une méthode de suppression sur `audit_log`.
- **Réécrire un producteur d'audit dans un service** au lieu de dépendre de `rations-audit-commun`, ou y surcharger `max.block.ms` et les autres bornes du producteur.
- **Faire dépendre `service-audit` de `rations-audit-commun`** (le consommateur doit rester un *tolerant reader* avec son propre type).
- **Ajouter un type métier, un DTO ou un utilitaire dans `rations-audit-commun`** : il ne porte que la publication d'audit, et le build le vérifie.
- **Consommer `/identite/habilitation` sans publier `ACCES_REFUSE`** sur verdict négatif ou sur indisponibilité du service Identité : le refus deviendrait intraçable.
- **Mettre en cache une réponse d'habilitation**, ou autoriser une action quand le service Identité ne répond pas (le refus conservateur est la règle, section 9.2 et `docs/appel-habilitation.md`).
- **Mettre en cache le seuil d'aiguillage**, ou lui donner une valeur de repli quand le paramètre est absent ou illisible : le refus (`500 SEUIL_INDISPONIBLE`) est la seule issue (décision Sprint 4.3).
- **Écrire une seconde comparaison montant/seuil** ailleurs que dans `AiguillageService`, fût-ce « pour vérifier » : deux chemins, c'est une divergence possible sur la règle qui commande le niveau d'approbation de la banque.
- **Poser `transmis_comptabilite` à la clôture** : il est posé par le **verrou de RG-13**, à la *réservation* — c'est-à-dire par le service qui publie, juste avant de publier (Sprint 5.3, révision de l'ordre du Sprint 5.1), et sur les **deux** branches du seuil. Le poser à la clôture le poserait avant même que l'état ne parte vers le service Transmission, et le verrou refuserait ensuite la vraie transmission comme un doublon.
- **Publier sans avoir obtenu le verrou**, ou le demander ailleurs que dans le chemin de requête du service Transmission : un verrou posé en amont par le service Workflow serait entièrement contourné par un appel manuel de `POST /transmission/processus/{id}` — l'un des chemins de double transmission que CT-22 vérifie.
- **Contrôler l'unicité en deux temps** (lire le drapeau, publier, puis l'écrire) : deux instances liraient toutes les deux « non transmis » avant que l'une ait pu écrire. Le verrou de ligne PostgreSQL est le seul mécanisme qui les sépare.
- **Libérer une réservation sur un échec ambigu** : un accusé peut se perdre *après* que le broker a écrit le message. Seul un échec **prouvé** antérieur à tout envoi se libère, et c'est le type `ResultatPublication` qui en répond, pas un commentaire.
- **Confirmer le verrou avant l'accusé du broker**, ou ne pas le confirmer du tout : dans un cas l'état paraîtrait publié sans l'être, dans l'autre il resterait signalé comme une publication d'issue inconnue alors qu'elle a abouti.
- **Réserver le verrou avant d'avoir épuisé les refus** (statut, détail, complétude de la charge) : chaque contrôle placé après la réservation allonge la fenêtre pendant laquelle un état est réputé transmis sans l'être, pour rien.
- **Rendre une erreur technique sur une seconde demande de transmission** : un rejeu légitime existe, et un code d'erreur ferait croire à une panne — donc inciterait à réessayer, c'est-à-dire au geste exact à décourager. `200` avec `resultat: DEJA_TRANSMIS`.
- **Faire porter le `securityMatcher` de la chaîne au secret partagé sur un chemin sans préciser le verbe** : `/processus/*/integration` porte désormais un `PUT` gardé par le secret et un `GET` gardé par OAuth2. Sans le verbe, la chaîne dédiée capterait le `GET` et le refuserait en `401` sans explication.
- **Rejouer une transmission dont on ignore si elle a atteint le broker** : l'idempotence du producteur Kafka ne couvre que les réessais internes d'un même `send()`. Un second `send()` applicatif produirait un second jeu d'écritures comptables pour les mêmes bénéficiaires. Le réessai est réservé aux échecs *antérieurs* à toute publication.
- **Faire échouer une clôture parce que la transmission a échoué** : le document porte déjà le visa, écrit hors transaction, et Kafka ne partage aucune transaction avec PostgreSQL. La clôture est la décision métier, la transmission sa conséquence.
- **Brancher la transmission sur le niveau qui a validé** au lieu du statut atteint : deux appels quasi identiques, et il suffirait d'en oublier un pour qu'une moitié des états ne parte jamais en paiement, sans aucune erreur visible.
- **Donner au pool de transmission une file d'attente**, ou un handler de rejet en `CallerRunsPolicy` : le premier ferait patienter des fils HTTP plusieurs minutes, le second exécuterait la transmission sur le fil de la requête — la fuite que ce pool ferme.
- **Injecter le mauvais `KafkaTemplate` dans service-transmission** : celui de l'audit est qualifié `kafkaTemplateAudit`, celui de l'échange comptable `kafkaTemplateEtatValide`. Les confondre publierait les états validés sur le topic d'audit, ou l'inverse.
- **Compter sur un bean `ObjectMapper` auto-configure** : Spring Boot 4 n'en fournit aucun de type `com.fasterxml.jackson.databind.ObjectMapper`. Le convertisseur de la charge comptable est construit explicitement, et c'est aussi bien : la forme du message qui part en comptabilite ne doit pas dependre d'un `spring.jackson.*` pose dans un fichier de deploiement.
- **Croire que `kafkaTemplate.send()` rend toujours un futur** : broker injoignable, il **leve des l'appel** un `KafkaException` enveloppant le depassement de `max.block.ms`. Capturer les seules exceptions du futur laisse remonter celui-la, et le refus specifie devient un `500` generique.
- **Poser un handler de rejet muet sur un pool dont on attend le resultat** : la tache disparait sans que personne ne l'attende jamais, et l'appelant patiente jusqu'a sa borne defensive. C'est l'inverse du pool d'audit, ou personne n'attend.
- **Publier la charge avec le `JsonSerializer` de spring-kafka** : il ajoute des en-têtes portant le nom de classe Java, que le module de comptabilisation n'a aucune raison de connaître. Sérialisation en chaîne, à la main.
- **Faire porter RG-12 sur toute la vie du processus** au lieu du cycle courant : le seul chef d'unité d'une agence serait bloqué à vie sur tout état qu'il a retourné, et le dossier deviendrait invalidable.
- **Rappeler le service d'aiguillage après la validation du Directeur Réseau** : il n'y a plus d'échelon, donc rien à arbitrer — et un seuil illisible bloquerait une validation qui n'en dépend pas.
- **Faire revenir un retour du Directeur Réseau au Chef d'Unité** : tout retour ramène à l'agent (RG-11), sans exception.
- **Laisser le rôle de l'appelant désigner le niveau de validation** : c'est le statut du dossier qui le désigne, le rôle est vérifié contre lui.
- **Rendre un motif de retour vide acceptable** parce que le champ est présent : `"   "` est un champ présent et un motif absent.
- **Enrichir le document d'un état resoumis après retour** au lieu de le régénérer : il afficherait les montants d'avant correction, ceux que le retour demandait justement de corriger.
- **Consommer `rations.etat.accuse` avec un `JsonDeserializer`** : il convertit *avant* que le code d'écoute ne soit appelé, donc un message malformé échoue dans le conteneur Kafka, hors de portée de toute capture, et bloque en boucle tous les accusés suivants. Chaîne obligatoire, conversion dans le code.
- **Laisser une exception sortir du consommateur d'accusé** pour autre chose qu'un service Workflow injoignable : toute autre issue est **définitive**, et rejouer ne ferait que bloquer la partition.
- **Poser `transmis_comptabilite` à la réception d'un accusé** portant sur un état jamais transmis : il ferait croire à un envoi qui n'a pas eu lieu, et RG-13 refuserait ensuite la vraie transmission comme un doublon — l'état resterait impayé à jamais.
- **Laisser un accusé écraser un statut d'intégration définitif** (`INTEGRE`, `REJETE`), ou faire régresser un statut vers `EN_ATTENTE` : le module n'a aucun moyen de savoir lequel des deux accusés dit vrai. Il refuse et signale, il n'arbitre jamais.
- **Publier une trace d'audit sur un accusé déjà appliqué** : un rejeu de topic est une opération d'exploitation courante, et une ligne par rejeu ferait croire à autant de traitements comptables.
- **Faire porter l'idempotence par une mémoire du service Transmission** (cache, table locale) : il n'a pas de base, et un cache disparaîtrait au premier redémarrage — c'est-à-dire au moment précis où un rejeu est le plus probable. La seule source de vérité est `processus_mensuel`, et la décision se prend dans la transaction d'écriture.
- **Faire figurer la valeur de `X-Cle-Interne` dans un journal, un message d'erreur, un événement d'audit ou un corps de réponse**, fût-ce sous forme de longueur ou de préfixe : un garde-fou qui fuit par le canal censé le surveiller n'en est pas un. Deux tests de garde relisent les sources.
- **Cocher un critère de validation portant sur l'audit sans avoir lu `rations_audit`.** Ni l'absence d'exception, ni l'absence de `WARN AUDIT PERDU`, ni un test à double vérifiant l'appel à `publier(...)` ne prouvent quoi que ce soit : les trois restent vrais quand le journal n'enregistre rien, et c'est exactement ce qui s'est produit des Sprints 1.3 à 6.2. La preuve est une requête, ou l'endpoint de consultation.
- **Redéclarer `id_utilisateur` ou `id_entite` en `NOT NULL` sur `audit_log`**, ou leur donner une valeur sentinelle (`-1`, `0`) : la première rejetterait les traces de refus d'accès de CT-04, les plus importantes du journal ; la seconde fabriquerait un utilisateur inexistant qu'une jointure prendrait pour réel.
- **Ouvrir un profil local au compte de contrôle du refus 403** (`thomas_ndzana`), par la migration `V1000` ou par un `INSERT` en base : la vérification d'environnement rendrait alors `200` là où elle attend `403`, sur un test de sécurité, sans aucun message. Besoin d'un profil pré-provisionné non lié pour éprouver une liaison ? Créer un compte jetable.
- **Trier le journal d'audit sur `id` ou sur l'offset Kafka** : l'ordre d'arrivée n'est pas l'ordre des faits, le pool d'audit étant asynchrone et multi-thread. `date_action` est la seule source de vérité chronologique.
- **Tracer une lecture de travail** (consultation d'un dossier, recherche de suivi, `date_dernier_acces`) : un événement par affichage d'écran noie les faits notables. On trace ce qui modifie un état, ce qui agrège une portée entière, ou ce qui fait sortir un fichier du système.
- **Renseigner `serviceEmetteur` à la main** dans un appel à `EvenementAudit.de(...)` : il est estampillé par le producteur depuis `spring.application.name`, et le confier à six appelants garantit qu'un l'oubliera.
- **Écrire un `@KafkaListener` sans `@EnableKafka`** : le projet déclare `spring-kafka` directement, sans `spring-boot-starter-kafka`, donc l'auto-configuration qui poserait cette annotation n'est pas entraînée. Le service démarre normalement et **n'écoute rien** - pas une ligne, pas une erreur. Vérifier l'écoute par le `KafkaListenerEndpointRegistry`, jamais par la seule présence des beans.

Il n'est **jamais rejoué automatiquement** — aucune reprise programmée n'est possible, le realm n'ayant pas de compte de service — et se lève à la main après vérification du topic. La requête de supervision (`CLOTURE` + transmis + statut d'intégration nul + réservation ancienne) est le seul moyen de le détecter, et rejoint en surveillance prioritaire celle des transmissions manquées du Sprint 5.1. |
| 6.1 | **Agrégation multi-services : stratégie A — le Workflow d'abord, la Saisie ensuite, filtrage en mémoire.** Aucune jointure SQL n'est possible entre `rations_workflow` et `rations_saisie`, et l'accès direct à la base d'un autre service est proscrit (AR04). Le Reporting demande les en-têtes au Workflow (qui applique la portée d'accès depuis le jeton relayé), puis n'appelle la Saisie **que si un critère de ligne est demandé** — nature, session, bénéficiaire. **Un ou deux appels HTTP, jamais davantage.** Un filtre portant sur les deux sources produit une **intersection stricte**. La pagination en mémoire est bornée à **5 000 en-têtes**, valeur de configuration et non constante compilée ; au-delà, `422 RECHERCHE_TROP_LARGE` nomme le volume et l'action attendue — un dépassement silencieux se lirait comme une absence de résultats. Voir `docs/decisions/2026-09-03-agregation-multi-services-du-reporting.md`. |
| 6.1 | **Service injoignable pendant une lecture : échec net, jamais un résultat partiel.** Workflow muet → `503 SERVICE_WORKFLOW_INDISPONIBLE`, aucun résultat n'étant concevable sans lui. Saisie muette **et** critère de ligne demandé → `503 SERVICE_SAISIE_INDISPONIBLE`, le message nommant les critères non appliqués et les deux issues. Motif décisif : le résultat partiel serait ici **plus large** que le demandé — tous les états de la période, y compris ceux sans aucune ration —, et affiché sous une étiquette « RATION » il est aussi trompeur qu'une liste trop étroite, mais bien plus difficile à repérer. Un drapeau ne protège que le lecteur qui pense à le lire. **Exception : Identité muette sur l'historique n'est pas bloquante** — l'historique s'affiche avec les identifiants d'acteurs au lieu des logins, le cloisonnement ayant déjà été tranché en amont par le Workflow ; faire échouer un dossier entier pour un libellé priverait le contrôle interne de ce qu'il consulte. Doctrine constante : refuser et signaler, jamais arbitrer (2.4, 4.3, 5.2). |
| 6.2 | **Structure du rapport : « envoyé à la comptabilité », jamais « transmis » ni « payé ».** `transmis_comptabilite = true` signifie seulement que le message est parti sur le topic ; un état peut être transmis **et** porter `statut_integration = REJETE` — rien n'a été payé. Un lecteur pressé lisant « 84 000 FCFA transmis » comprendrait « versés aux agents ». La synthèse porte donc sept lignes, dont une **ligne distincte « Montant rejeté par la comptabilité »** au même niveau que les autres montants, et non noyée dans la répartition par situation d'intégration. **Un seul calcul, trois usages** (CT-32) : `RapportService.produire` rend un `Rapport` dont tous les totaux sont déjà calculés ; PDF et Excel ne font que le rendre, sans jamais réadditionner un montant. Période sans état : `200` avec `vide = true` et une synthèse à zéro (CT-33), jamais une erreur. Voir `docs/decisions/2026-09-04-structure-du-rapport-d-activite.md`. |
| 6.2 | **Nommage des fichiers exportés : `rapport-rations-<agence>-<AAAAMM>.<pdf\|xlsx>`**, `<agence>` valant `toutes-unites` quand aucune n'est demandée. Période en `AAAAMM` sans séparateur, pour que le tri alphabétique d'un dossier soit un tri chronologique. Le fichier est rendu en téléchargement (`Content-Disposition: attachment`), **jamais écrit sur disque** : ce service n'a ni base ni stockage où le conserver — c'est le seul du module dans ce cas, et la seule convention de nommage qui ne soit pas celle des pièces jointes du Sprint 4.2. |

| 6.3 | **Un critère de validation portant sur l'audit exige désormais une requête sur `rations_audit`.** Constat qui la motive : les Sprints 1.3 à 6.2 ont tous coché leurs critères d'audit alors que `audit_log` n'a jamais reçu une ligne. Ce qui était réellement observé — aucune exception levée, aucun `WARN AUDIT PERDU`, un test à double vérifiant l'appel à `publier(...)` — **reste vrai quand le journal n'enregistre rien**. Le producteur étant conçu pour ne jamais faire échouer le métier (cinq couches), l'absence de bruit ne prouve rien : **un dispositif dont la panne est silencieuse par construction ne se valide pas par le silence.** Voir `docs/decisions/2026-09-04-verification-reelle-de-l-audit.md`. |
| 6.3 | **Migration V2 de `rations_audit` : `id_utilisateur` et `id_entite` deviennent nullables.** La V1 les déclarait `NOT NULL` en contradiction avec le contrat de fil publié par les six services ; opposé au schéma, un message `ACCES_REFUSE` réellement présent sur le topic était rejeté par PostgreSQL. **21 des 30 traces passent un `null` littéral en `idUtilisateur`, 7 en `idEntite`.** Aucune valeur sentinelle.
